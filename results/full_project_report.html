Part I — System Architecture

The complete pipeline, from document upload to final report, stage by stage.

1. Design Philosophy

The system is framed not as a venture-success predictor but as a measurement instrument: it produces evidence-grounded, provenance-linked scores intended to support (not replace) human reviewer judgment. The project's own research paper states this explicitly: the central research question is "Can an evidence-grounded LLM evaluation system serve as a credible outcome-free measurement instrument for venture proposal review?" — deliberately narrower than "can an LLM predict which ventures will succeed."

Provenance-preserving design: rather than asking an LLM to read a proposal and output a score in one shot, the pipeline decomposes the task into nine auditable stages, each storing an intermediate artifact on disk (raw facts, dimension summaries, generated questions, candidate answers, selected answers, expert commentary, rubric scores) rather than passing only free-form text between stages. This means every score can be traced back to the specific extracted facts and generated evidence that produced it — a design explicitly modeled on FActScore's atomic-fact decomposition and RAGAS/ARES's separation of context quality from answer faithfulness.

Two validation philosophies used in this project: (1) Outcome-free auditing — comparing AI scores against human expert judgments on the same 12 proposals, used because real venture outcomes (acquisition, failure, sustained revenue) take years to materialize and are confounded by post-investment events. (2) Outcome-based validation — comparing AI scores against real, already-known outcomes (Kickstarter campaign funding results), which this project added specifically because it provides an objective, scalable ground truth the outcome-free approach cannot.

2. Formal Task Definition & Validity Framework

The project's research paper formalizes the screening task with explicit notation, useful for framing any academic writeup precisely rather than describing the system only in prose.

D_i = proposal i (pages/slides + extracted evidence) H_i = expert assessment of proposal i Five ordinal dimensions, each normalized to [0,1]: Team, Objectives, Strategy, Advantages, Feasibility System output for proposal i: Ĥ_i = { ĥ_team, ĥ_objective, ĥ_strategy, ĥ_advantages, ĥ_feasibility, r̂_i, ĉ_i, ŷ_i } where r̂_i ∈ [0,1] overall screening score ĉ_i ∈ [0,1] confidence ŷ_i ∈ {GO, NO-GO} binary recommendation

Four score-validity targets

Rather than asking one blanket question ("is the AI accurate?"), the evaluation framework decomposes validity into four independently testable targets — each with its own dedicated metric and its own Part-IV results section in this document:

4. Stage 0 — Document Ingestion & OCR

Script: src/tools/prepare_proposal_text.py (667 lines). Input: the uploaded proposal file (PDF, DOCX, PPTX, TXT, or Markdown). Output: src/data/prepared/<pid>/full_text.txt, pages.json (per-page text, source tag, global character offsets), and stage0_audit.json (per-page character counts and low-text page flags).

PDF extraction and OCR fallback

Text is first extracted natively via pdfplumber. If a page's extracted text falls below MIN_TEXT_CHARS_PER_PAGE = 30 characters (a proxy for "this page is a scanned image, not real text"), the page is rendered to an image and passed through OCR via pdf2image + pytesseract. The OCR language is set to chi_sim+eng by default (mixed Simplified-Chinese and English), reflecting that the proposal corpus is bilingual. When both native and OCR text are short, a helper keeps whichever is longer to avoid discarding useful labels.

Vision-model pass for charts, tables, and figures

Any page containing embedded images is optionally (default: enabled) rendered at 150 dpi and sent to a vision-capable LLM with a prompt instructing it to describe "ALL visual content present: charts, graphs, tables, figures, diagrams, flowcharts," including specific numbers, axis labels, and trends. The resulting description is appended into the page's text as a tagged [VISUAL CONTENT: ...] block, so downstream stages can reason about a chart's content even though they only ever see text. Vision calls auto-disable after 3 consecutive failures to avoid wasting the rest of a run retrying a broken call. DOCX and PPTX documents get analogous treatment: paragraphs and tables are extracted as text; inline pictures go through the same vision pipeline.

Source: prepare_proposal_text.py:48,65,68,70-72,97-113,222-392,395-529,578-622.

5. Stage 1 — Atomic Fact Extraction

Script: src/tools/extract_facts_by_chunk.py (1074 lines). Input: Stage 0's full_text.txt. Output: src/data/extracted/<pid>/raw_facts.jsonl and stage1_audit.json.

The proposal text is split into overlapping chunks, and the LLM is asked to extract atomic facts from each chunk — single, source-checkable propositions rather than interpretive statements. Each fact is tagged with: (a) a subset of the five review dimensions it's relevant to (team, objectives, strategy, innovation, feasibility), (b) a type from a 19-value enumeration (team_member, milestone, tech_route, ip_asset, risk, mitigation, etc.), and (c) source metadata (chunk index, character range) linking it back to the exact source text. This atomic decomposition is the mechanism that later lets the pipeline separate "the proposal reports three patents" (a checkable claim) from "the intellectual-property position is defensible" (an evaluator judgment) — the same distinction the project's paper models on FActScore. Chunks yielding suspiciously few facts (below a low-fact warning threshold) are retried, and missing dimension labels are inferred from keywords when the LLM under-labels a fact.

Source: extract_facts_by_chunk.py:1-24,73,79-100.

6. Stage 2 — Dimension Construction

Script: src/tools/build_dimensions_from_facts.py (746 lines). Input: Stage 1's raw_facts.jsonl. Output: dimensions_v2.json, dimension_facts.json, and a copy at src/data/parsed/parsed_dimensions.clean.llm.json.

Stage-1 facts are bucketed into the five review dimensions, then the LLM is called once per dimension with a strict grounding prompt that explicitly forbids inventing organizations, numbers, or technologies, and forbids speculative language ("likely," "probably") unless it is present in the source facts. This produces a summary, key_points, risks, and mitigations per dimension — the evidence packet that all downstream scoring is ultimately based on. dimensions_v2.json is the file the Stage 6 investment-scoring call reads directly (bypassing the QA-answer pipeline), so its quality has an outsized effect on the final rubric scores.

Source: build_dimensions_from_facts.py:1-19,141-200.

7. Stage 3 — Question Generation

Script: src/tools/generate_questions.py (1461 lines). Input: dimensions_v2.json. Output: generated_questions.json (simplified list) and generated_questions_detail.json (full metadata: qid, aspect, answer_type, links_to).

Questions are generated per dimension and must explicitly link back to specific key_points, risks, or mitigations via index references (links_to) — another provenance-preservation mechanism, ensuring every question has a traceable reason for existing rather than being a generic template question.

Source: generate_questions.py:32-36.

8. Stage 4 — LLM Answering

Script: src/tools/llm_answering.py (2274 lines, typically the slowest stage). Input: generated questions + dimension evidence. Output: per-provider raw answer files (chatgpt_raw.json, gemini_raw.json, deepseek_raw.json) merged into all_refined_items.json.

Every generated question is answered using only proposal facts, plus general domain knowledge for explanatory context — explicitly forbidden from inventing new experiments, numbers, organizations, registrations, or evidence, and with no web search access. All configured providers run concurrently; their candidate answers are merged for the selection step in Stage 5. This structured-answer schema (separating direct response, factual claims, evidence pointers, confidence, and caveats) mirrors RAGAS/ARES's separation of context quality from answer faithfulness.

Source: llm_answering.py:1-19.

9. Stage 5 — Post-Processing & QA Scoring

Script: src/tools/post_processing.py (1727 lines). Input: Stage 4's merged candidate answers. Output: metrics.json, selected_by_question.json, final_payload.json, report.md, drops_debug.json.

This is where per-answer quality scoring and dimension/overall QA-score aggregation happen — the numbers that feed into (but are ultimately dominated by) Stage 6's investment-rubric score.

Per-answer scoring formula

Each candidate answer receives sub-scores for length norm (s_len), claim count norm (s_clm), evidence count/authority/coverage (s_evc/s_eva/s_evg), structure (s_str), question/claim/evidence alignment (s_aln), and calibrated confidence (s_cal), combined as a weighted sum:

fields_part = 0.16·length + 0.20·claims + 0.10·evidence_count + 0.02·evidence_authority + 0.02·evidence_coverage + 0.17·structure + 0.28·alignment + 0.05·calibrated_confidence

This is then blended with a peer-consistency score (Jaccard similarity vs. other candidate answers to the same question, weight 0.10):

total = 0.90 × fields_part + 0.10 × consistency_score

Penalties are then subtracted: contradiction −0.05, overclaim −0.03, understructure −0.03, redline_residual −0.06, dimension_drift −0.04 (clipped to [0,1]). This total is used to select the best candidate answer per question; each dimension's avg QA score is the mean of its selected answers' totals.

Dimension weights (used at both Stage 5 and Stage 6)

team = 1.00 objectives = 1.00 strategy = 1.00 innovation = 1.10 feasibility = 1.20

Stage 5's overall_score (QA-based, pre-Stage-6-blend)

overall_score = Σ(dimension_avg × dimension_weight) / Σ(dimension_weight)

overall_confidence is computed separately as a blend of mean per-answer confidence (weight 0.5), mean pairwise Jaccard cross-provider agreement (weight 0.3), and one minus the mean pairwise contradiction rate (weight 0.2).

Source: post_processing.py:195-211,700-768,1275-1301.

10. Stage 6 — AI Expert Opinion & the Investment Rubric

Script: src/tools/ai_expert_opinion.py (1239 lines, internally versioned "Stage 6 - AI Expert Opinion v4.1"). This is the core rubric-scoring stage and the single most important piece of the pipeline for understanding how final scores are produced. It makes two separate LLM calls.

Call A — Dimension commentary (qualitative, non-scoring)

Produces the expert-style narrative (strengths, concerns, recommendations) at temperature=0.25 (non-zero — the source of the pipeline's known run-to-run non-determinism). This call is explicitly forbidden from outputting "question IDs, numeric scores, percentages, or internal metric names," so that its qualitative narrative cannot leak score information into itself. On failure it falls back to a deterministic local rule-based generator.

Call B — Investment-grade scoring (INVEST_SCORE_SYSTEM)

A fully separate call at temperature=0.0, seed=42 (i.e., deterministic), reading dimensions_v2.json facts directly — bypassing the QA-answer pipeline entirely, to avoid document-quality/verbosity bias contaminating the investment judgment. This call contains the full scoring rubric, reproduced in complete detail below.

The rubric's own preamble instructs the model: "Score each dimension 0.0–1.0 based ONLY on the proposal facts provided. Be discriminating: most proposals should land in 0.40–0.70. Scores above 0.80 require strong, specific evidence. Do NOT be generous... Resist the urge to cluster scores near 0.65-0.75." This single instruction is the reason overall scores across every dataset in this project cluster in the 0.4–0.7 range rather than approaching 1.0 — it is a deliberate design choice in the rubric, not a limitation of the scoring model.

Team

T-A (0.83–0.95): ANY of three qualifying sets — (1) academic research leader: CAS/national-academy/MIT-Harvard-Stanford-caliber PI + 50+ publications or major patents; (2) deep industry domain leader: 25+ years expertise + demonstrable commercial success at scale; (3) world-class operational excellence: DPPM<10, >1B units shipped, >20 tier-1 customers, cross-functional leadership.
T-B (0.65–0.80): major-university professor (985/211 tier), OR senior executive (10+ yrs CXO/VP/Director), OR founder with a prior exit, OR company with 15+ years domain history.
T-C (0.45–0.62): credible practitioners without exceptional-performance proof — e.g. a clinical expert with a limited publication record, or an industry team without a large-scale execution track record.
T-D (0.20–0.42): vague or unverifiable credentials, or AI/software applied to a domain without deep domain expertise.

Innovation (mapped to "Advantages" at Stage 8 / in the human rubric)

Two preliminary rules apply before categorization. RULE 1 — the "AI-powered auto-cap": if the primary commercialized product is an AI software system (clinical decision support, hospital management, industrial process optimization — i.e. "AI IS the product"), the dimension is automatically capped at I-C (0.42–0.56) regardless of engineering sophistication. RULE 2 — the exception: if AI/ML is merely a computational design tool used to engineer a physical product (an enzyme, protein, drug molecule, material, or piece of hardware) and that physical output is what's being commercialized, the I-C cap does not apply — the physical/biological/chemical innovation is scored on its own merits.
I-A (0.83–0.95): requires ALL three: (1) a genuinely new mechanistic class (the "HOW," not just the "WHERE"), (2) an explicit IP claim (filed/granted patents or documented independent IP rights), (3) quantitative proof (specific numeric performance data). Missing any one disqualifies I-A.
I-B (0.63–0.80): novel but missing one I-A condition.
I-C (0.40–0.60): application-layer innovation, including most AI proposals. Explicit hard cap: "Any proposal described as 'AI-powered', 'intelligent platform', 'data-driven', 'multimodal data integration', or 'machine learning for [clinical/industrial task]' → score 0.42–0.56, NO EXCEPTIONS."
I-D (0.20–0.38): incremental or commodity, no novel mechanism.

Objectives (three bands only, no D)

O-A (0.78–0.92): quantified market gap, named buyer/payer pathway, documented unmet need with regulatory/clinical evidence.
O-B (0.58–0.75): clear problem + market-size estimate, but vague/aspirational buyer pathway.
O-C (0.38–0.55): real problem but undefined/speculative market size, no buyer evidence.

Strategy (three bands; scored on soundness/defensibility, not documentation completeness)

S-A (0.78–0.92): strong on ALL of: defensibility (moat — first-mover IP, in-progress regulatory approval, exclusive channel, demonstrated network effects), execution realism (strategy matches team capability), and at least one market-validation signal (named production customer, filed regulatory submission, or existing paying customers).
S-B (0.58–0.75): coherent strategy with partial moat or partial execution evidence.
S-C (0.38–0.55): aspirational/generic strategy ("partner with hospitals," "sell to enterprises") without differentiation evidence.

Feasibility (four bands)

F-A (0.78–0.92): itemized budget, realistic multi-year milestones, named regulatory pathway, existing infrastructure or confirmed manufacturing partner.
F-B (0.58–0.75): reasonable budget with partial detail, milestones exist.
F-C (0.38–0.55): budget stated without breakdown, vague timeline, risks acknowledged but not mitigated.
F-D (0.20–0.35): unrealistic or missing budget, unresolved critical dependencies.

The model must return, per dimension: a numeric score (0–1), a category letter code, and a rationale citing specific evidence.

Blending investment score with QA score

INVEST_WEIGHT = 0.90 blended_dim_score = 0.90 × invest_score[dim] + 0.10 × qa_score[dim]

i.e. the deterministic, fact-grounded investment rubric dominates (90%) over the QA-answer-quality score (10%). All three values — score_echo, qa_score_echo, and invest_score_echo — are stored per dimension for audit and downstream calibration (this is what calibration_sweep.py reads back without making any new LLM calls).

The same dimension weights from Stage 5 (team=1.0, objectives=1.0, strategy=1.0, innovation=1.10, feasibility=1.20) are re-applied to the blended per-dimension scores to produce the final blended_overall score, which is what feeds the verdict rule below. overall_confidence is carried over unchanged from Stage 5.

Source: ai_expert_opinion.py:102-228 (full rubric),231-306,519,644-718,1018-1131,1056.

12. Stage 8 — LLM Rubric Scoring

Script: src/tools/generate_llm_scores.py (312 lines standalone; fan-out version generate_multi_provider_scores.py in the legacy execution mode). Input: the compiled Stage 7 report Markdown (trimmed to 12,000 characters) plus the expert-opinion summary/verdict/risks/strengths. Output: src/data/llm_scores/<pid>/llm_scores.json.

This stage asks the LLM to score the report (not the raw proposal facts) directly on the same scale used by human experts: five dimensions on a 1–5 scale, an overall ranking on a 1–20 scale, and a binary GO/NO-GO verdict. The system prompt gives explicit calibration anchors (1–2 = critical gap, 3 = common/screened-proposal quality, 4 = meaningfully strong, 5 = exceptional) and instructs a "Y" verdict when at least 3 of 5 dimensions score 4 or above. On failure, it falls back to a deterministic linear remap of Stage 6's blended scores (1 + score×4 for the 1–5 scale, 1 + score×19 for the 1–20 scale).

Dimension name mapping used at this stage (and in all evaluation code that compares against the human rubric): team→team, objectives→objective, strategy→strategy, innovation→advantages, feasibility→feasibility. This is the single place the internal name "innovation" becomes the externally-reported name "advantages" — important to note consistently when writing about the pipeline, since the two names refer to the same dimension throughout.

Source: generate_llm_scores.py:1-17,104-134,175-196; README.md:22-40 (mapping table).

13. The Verdict Rule & Score Formulas

The pipeline's final decision layer — verdict_rule(), at ai_expert_opinion.py:732-749 — converts the blended overall score and confidence into one of three verdicts:

def verdict_rule(score, conf, dims): inv = dims["innovation"]["avg"] # blended (post Stage-6) value fea = dims["feasibility"]["avg"] # blended (post Stage-6) value if score >= 0.725 or conf >= 0.811: return "GO" if score < 0.40 or inv < 0.30 or fea < 0.30: return "NO-GO" return "HOLD"

GO fires on an OR-condition: either the overall score clears 0.725, or confidence alone clears 0.811 — either is sufficient. NO-GO fires if the score is very low, or if either innovation or feasibility individually falls below 0.30, regardless of the overall score. Everything else is HOLD.

Where these exact numbers came from

The 0.725/0.811 pair was not hand-picked — it was produced by calibration_sweep.py's sweep_verdict_thresholds() function, a 2-D grid search over candidate score/confidence thresholds combined with OR logic, run against the 12-proposal human-expert dataset to maximize verdict accuracy. This zero-LLM-call sweep reads cached invest_score_echo / qa_score_echo values, so re-running it costs nothing. It replaced an earlier AND-rule (score ≥ 0.65 AND confidence ≥ 0.65), improving verdict accuracy from 58.3% to 83.3% on the 12-proposal set (full comparison in Section 24).

Important nuance for accuracy when writing about this system: this OR-logic threshold pair was calibrated exclusively on the 12-proposal biotech/semiconductor dataset, in-sample (fit and evaluated on the same 12 proposals, with no held-out check). When this exact threshold was later applied unmodified to the 141-proposal Kickstarter dataset, it produced zero GO verdicts, because Kickstarter proposals structurally never reach scores anywhere near 0.725 (see Sections 25 and 27). This is the central empirical finding motivating the entire Kickstarter calibration study in Part IV.

14. Operational Footprint

Per the project's own research paper (Section 4.7), the 12-proposal OpenAI evaluation run made 1,868 logged LLM calls in total, averaging ~156 calls per proposal, with a mean per-call latency of 8.74 seconds (median 7.46 seconds); calls are partially parallelized across stages. No aggregate token or dollar cost is reported for the batch (a documented gap).

Separately, a performance engineering pass (documented in docs/pipeline_time_sink_analysis.md) root-caused two major bottlenecks — a stalled Stage 1 OpenAI call (fixed via a 120-second OPENAI_TIMEOUT_SECONDS) and a Stage 4 batch-call schema mismatch (fixed directly in llm_answering.py) — and introduced concurrency controls (STAGE1_CHUNK_WORKERS=4, STAGE4_DIM_WORKERS=2, STAGE4_VARIANT_WORKERS=3, STAGE4_REFINE_WORKERS=3). Total wall-clock time for a full proposal run dropped from ~10h 4m to ~28m 32s (a ~21× speedup) between two benchmarked runs.

Source: research_paper.pdf Section 4.7; docs/pipeline_time_sink_analysis.md.

15. Related Work & Positioning

The project's research paper positions this work against three literatures. Reproducing that positioning here is useful context for framing related-work sections of any derived paper.

Financial LLMs and venture screening

Domain-specific financial LLMs (BloombergGPT, FinGPT, PIXIU) and finance benchmarks (FinEval, CFBenchmark, FinBen) establish that finance is an active LLM-specialization area, but target general financial NLP rather than proposal screening specifically. Grounded financial QA work (FinanceRAG, Multi-Reranker) targets retrieval correctness, not investment scoring. FAITH is directly relevant: it shows LLMs produce unsupported numerical answers even with source tables in context, worse as reasoning moves from direct lookup to compositional use — the same hallucination risk this project's groundedness audit (Section 24) checks for directly in the venture-screening setting. A separate investment-bias study found LLMs tend to preserve an initial investment preference despite counter-evidence, arguing investment agents should be evaluated on intermediate behavior, robustness, and human collaboration — not just final-task accuracy, a framing this project's whole "outcome-free audit" design follows.

DIALECTIC is the closest prior startup-evaluation system: it structures startup facts, question trees, pro/con reasoning, critique, and numeric investment scores — architecturally similar to this pipeline's fact→dimension→question→answer→score decomposition. The paper's stated point of novelty relative to DIALECTIC and similar systems: "Our novelty is not another multi-agent scoring architecture. We instead treat the produced score as the object of validation." VCBench and founder-success-prediction work are noted as adjacent but explicitly out of scope — this project audits measurement validity, it does not attempt outcome prediction (with the partial exception of the Kickstarter real-outcome study added in this session, which is itself framed as a validity check, not a launched predictor).

Grounded and trustworthy financial decision support

RAGAS and ARES's separation of context quality from answer faithfulness underlies the Stage 4 answering schema (Section 8). FActScore's atomic-fact decomposition underlies Stage 1 (Section 5) and the claim-grounding taxonomy (Section 24). SelfCheckGPT (claim-level hallucination detection without external references) is cited as a related but distinct approach the groundedness audit does not directly implement. Prior ICAIF-adjacent work on investment-risk models varying by country/gender, balanced arguments revealing latent investment preferences under counter-evidence, and transparency/prompt-design effects on human-AI investment decisions all motivate treating this system's outputs as decision-support signals requiring audit, not authoritative judgments.

Human-AI agreement and the measurement gap

A cited systematic review warns that task formulation, metric choice, benchmark construction, and reporting practices can produce contradictory conclusions across LLM-evaluation studies — part of the paper's motivation for reporting agreement, ranking, calibration, and dimension reliability as separate numbers rather than collapsing them into one "the AI is good/bad" verdict (see the four-target validity framework, Section 2). LLM-as-judge literature (G-Eval, MT-Bench, Chatbot Arena, Prometheus-style rubric evaluation) is cited as the closest methodological neighbor for the sensitivity/content-injection checks, alongside the caveat that using human expert scores as the operational reference (rather than another LLM judge) avoids compounding one LLM's biases with another's.

Part III — Evaluation Methodology

How each study was designed, and why.

18. Methodology A — Human-Expert Agreement

All comparisons between AI and human-expert scores use the following metrics, computed by evaluate_cohens_kappa.py (despite its name, it computes more than kappa):

  • Quadratic-weighted Cohen's κ — both AI and human scores are discretized onto a 5-point grid (0, 0.25, 0.50, 0.75, 1.00) before computing agreement beyond chance, with bootstrap 95% confidence intervals. The paper explicitly flags κ as noisy here because AI scores are heavily concentrated in one or two bins (sparse marginal occupancy).
  • ICC(2,1) (Intraclass Correlation) — used specifically for the continuous overall-ranking score, with a 95% CI, as a measure of absolute-value agreement rather than just ranking agreement.
  • Spearman rank correlation (ρ) with p-value — the primary ranking-agreement metric, computed on raw 0–1 floats (not binned), for each of the 5 dimensions plus the overall ranking.
  • Paired mean-difference bias check — mean(AI−human), tested with a paired t-test (and a Wilcoxon signed-rank sensitivity check), to detect systematic score-scale offset.
  • Pairwise rank concordance — of all pairs of proposals the human ranked in a definite order (ties excluded), what fraction does the AI rank in the same relative order? Directly measures whether screening priority ordering is preserved.
  • Verdict classification metrics — accuracy, precision, recall, F1, and the full confusion matrix, comparing the AI's binary GO/NO-GO verdict against the human "Funded Y/N" label.

Multiple-testing correction: the six Spearman tests (5 dimensions + overall) are treated as one family and corrected using the Holm method — chosen as more powerful than Bonferroni while still conservative. The six paired mean-difference tests form a second Holm-corrected family.

Statistical power context: at n=12, a two-sided correlation test needs |ρ| ≈ 0.73 for 80% statistical power at α=0.05 (Fisher-transformation calculation) — explicitly noted in the paper as a reason to treat single-dataset correlation results here as exploratory, not confirmatory.

Source: research_paper.pdf Section 5; evaluate_cohens_kappa.py:1-27.

19. Methodology B — Real-World Outcome Validation (Kickstarter)

evaluate_kickstarter_correlation.py compares AI scores against real funding outcomes, computed separately for Toronto, Montreal, and combined:

  • Overall Spearman correlation between the AI's overall_score (0–1) and actual funded (%), with p-value and Holm-corrected p-value. Spearman (rank-based) is used instead of a linear correlation because funded % is extremely right-skewed — most campaigns raise 0–150% of goal, a handful raise over 1000%.
  • Per-dimension Spearman — each of the 5 dimension scores correlated individually against funded %, to see which dimensions carry real predictive signal in this domain.
  • Binary classification — treating the AI's GO verdict as a prediction of funded % ≥ 100, with the full accuracy/precision/recall/F1 confusion-matrix breakdown.

Source: evaluate_kickstarter_correlation.py:1-25.

20. Methodology C — Threshold Calibration via Cross-Validation

calibrate_kickstarter_threshold.py re-derives a Kickstarter-appropriate GO decision threshold, keeping the exact same OR-logic shape as production (score ≥ τr OR confidence ≥ τc) but searching for new values of τr, τc instead of reusing the biotech-derived 0.725/0.811 pair.

Why cross-validation instead of a single train/test split: only 24 of 141 Kickstarter proposals actually succeeded. A single 70/30 split would leave as few as 7 successes in the test set — too few for a stable precision/recall estimate. Instead, stratified 5-fold cross-validation (seed=42) is used: the 141 proposals are split into 5 folds, each with a proportional (~17%) share of successes. For each of the 5 rounds, one fold is held out as test data, the other 4 are used to grid-search the F1-maximizing (τr, τc) pair (candidate thresholds are midpoints between consecutive sorted training-fold values, so every real decision boundary in that fold is tested), and the chosen threshold is applied only to the held-out fold. Every proposal is evaluated exactly once, using a threshold that never saw it. The 5 test-fold confusion matrices are summed into one aggregated result.

Why F1, not accuracy, is the calibration objective: only 17% of campaigns succeed, so "always predict failure" already scores 83% accuracy without ever identifying a real success — exactly the failure mode of the original transferred threshold. F1 (the harmonic mean of precision and recall) forces the calibration to actually find successes.

Three scenarios are reported side by side: (1) before — the unmodified production threshold; (2) in-sample — threshold grid-searched and evaluated on the same 141 proposals, reported only as an overfitting-risk reference; (3) cross-validated / held-out — the honest, generalizable result.

Source: calibrate_kickstarter_threshold.py (full docstring and implementation).

21. Methodology D — Score Improvement Testing

improve_kickstarter_score.py tests whether the underlying score itself (not just the threshold) can be improved, given that the earlier correlation study (Section 25) found team and objective carry no significant relationship with real Kickstarter outcomes while feasibility, strategy, and advantages do. Three scoring methods are compared head-to-head, all evaluated via the same 5-fold CV (same folds/seed), using a single score threshold (no confidence OR-gate, to isolate score quality alone):

  • Method A — overall_score: the unmodified production score (baseline).
  • Method B — simple composite: a plain, unweighted average of feasibility + strategy + advantages only, dropping team and objective. Initially computed using dimension-selection derived from the full 141-proposal correlation study (a design choice later shown to be a soft form of leakage — see Section 22).
  • Method C — logistic regression: an L2-regularized model (regularization strength C=1.0, fit via scipy.optimize.minimize) that learns its own weights across all 5 standardized dimension scores, fit strictly within each training fold (never seeing its own test fold), producing pooled out-of-fold predicted probabilities for evaluation.

Discrimination is additionally measured in a threshold-free way via ROC-AUC (the probability a randomly chosen success scores higher than a randomly chosen failure — computed via the rank-based Mann-Whitney formula) and Average Precision, both independent of any specific decision threshold.

Source: improve_kickstarter_score.py (full docstring and implementation).

22. Methodology E — Robustness Checks (Bootstrap & Nested Validation)

kickstarter_score_robustness_check.py performs two rigor checks specifically on the Method B result, after recognizing that its "no fitting" claim was incomplete — the choice of which three dimensions to keep was itself made using full-dataset correlations, a softer form of the same leakage problem the threshold-calibration study exists to prevent.

Check 1 — Bootstrap confidence intervals

Each pairwise ROC-AUC difference (B vs A, B vs C, C vs A) is bootstrapped 10,000 times: resample the 141 proposals with replacement, recompute both methods' AUC on the identical resample, record the difference, repeat. The resulting distribution gives a 95% confidence interval on the true AUC gap and a "probability the second method is better" estimate (fraction of resamples where it was). A gap is only called statistically significant if the 95% CI excludes zero.

Check 2 — Per-fold dimension-selection stability, and a fully-nested re-evaluation

The "which 3 dimensions?" decision is independently re-derived 5 times, using only each training fold's own data (Spearman correlation between each dimension and funded_pct, computed on the training fold only, keeping the top 3 by correlation). This checks whether the same three dimensions are picked when the full dataset isn't visible. A fully-nested Method B is then evaluated: for each fold, both the dimension selection and the decision threshold are fit using only that fold's training data, and the resulting composite score is evaluated only on the held-out fold — the methodologically strongest version of Method B, with no part of the number touching the full 141-proposal dataset at any point.

Source: kickstarter_score_robustness_check.py (full docstring and implementation).

23. Methodology F — Groundedness & Content-Sensitivity Audits

Two further outcome-free audits are documented in the project's existing research paper, applied only to the 12-proposal biotech/semiconductor dataset:

Claim grounding

Report statements are classified into four categories: verifiable facts, numerical inferences, professional inferences, and evaluator judgments. Only verifiable facts and numerical inferences count toward the groundedness denominator (professional inferences are analyst judgments; scores/confidence/verdicts are evaluator outputs, not source-document claims, and are excluded). Each eligible claim is labeled supported, partially supported, or unsupported:

Strict groundedness G_strict = N_supported / N_eligible Lenient groundedness G_lenient = (N_supported + 0.5·N_partial) / N_eligible Unsupported rate U = N_unsupported / N_eligible

Controlled content sensitivity

PLUS/MINUS proposal-specific variants are constructed at the report/rubric input level for Strategy, Objectives, and Advantages (each with 8 fine-grained sub-rubrics). PLUS injects concrete favorable evidence (revenue model, regulatory pathway, IP status, benchmark result, market estimate, buyer pathway); MINUS replaces the strongest available evidence with explicit absence statements. The check measures whether scores move in the theoretically expected direction. This check is explicitly prompt-coupled, not independent: because the generation prompt names the target rubric and the desired direction, it measures generation–scoring consistency under rubric-targeted edits, not whether realistic new evidence encountered "in the wild" would move scores the same way.

Two sensitivity-generation modes

The tooling (run_sensitivity_all_dimensions.py) supports two modes: Default (hardcoded) — fixed content, 2 sub-rubrics tested per dimension across strategy/advantages/objectives; and Adaptive (--adaptive flag) — the LLM generates proposal-specific PLUS/MINUS content covering all 8 sub-rubrics per dimension (16 checks per proposal), giving denser coverage at the cost of variable, LLM-generated injected text rather than a fixed script.

The 8 sub-rubrics per dimension (R1–R8)

Each of Strategy, Advantages, and Objectives is additionally scored on 8 fine-grained sub-rubrics, split into two groups with different expected AI-vs-human agreement:

  • R1–R4 (document-verifiable): milestone dates, revenue model, regulatory pathway, market size — facts that are either stated in the document or not. The AI is expected to track human scoring closely here, since both raters are reading the same explicit text.
  • R5–R8 (judgment-dependent): competitive-moat credibility, team-strategy fit, market timing — and named specifically in the README as the weakest cells: Problem-Solution Fit, Market Timing, and Competitive Defensibility. These require inference and domain judgment beyond what's explicitly written, and the AI is expected to diverge more from human raters here.

A blank human_scorecard_template.csv exists in the repository specifically to collect a second human rater's sub-rubric scores, so a human-vs-human agreement ceiling can eventually be computed and compared against the AI-vs-human numbers — this has not yet been done (see Limitations, Section 33).

How PLUS/MINUS variants are actually constructed (implementation detail)

An internal implementation review (sensitivity_analysis_report.html) documents the exact mechanics, which sharpen the "prompt-coupled" caveat above into something more specific and mechanistic:

  • PLUS injection prepends a fixed block of pre-written evidence text immediately before a specific report section heading (falling back to inserting before the Q&A section if that heading isn't found). The injected text is identical across all 12 proposals for a given dimension — it is not proposal-specific, generated evidence.
  • MINUS stripping only removes narrative bullet/numbered lines containing specific target keywords and applies a fixed list of inline regex substitutions. It does not touch the report's Q&A evidence section, which frequently re-states the same underlying concepts in different vocabulary — so a MINUS variant can leave much of the model's actual evidence base intact even when the narrative section reads as stripped. If a proposal's narrative never used the targeted keywords in the first place, its MINUS variant is byte-for-byte identical to its baseline.
  • Variant re-scoring captures only the numeric score, not the evidence/reasoning fields the baseline scorer captures — a deliberate speed tradeoff that means root-cause analysis of any given score movement (or non-movement) has to be inferred from the report text and rubric definitions after the fact, not read directly off a captured explanation.

Source: research_paper.pdf Sections 5.4, 5.5; README.md "Research & Calibration Tools"; results/Dataset1/sensitivity_analysis_report.html.

What the two evaluation programs together imply.

31. Cross-Dataset Comparison

The two evaluation programs in this project — human-expert comparison on 12 biotech/hardware proposals, and real-outcome comparison on 141 Kickstarter campaigns — used the exact same unmodified pipeline and rubric, which makes their differences directly informative about what generalizes and what doesn't.

The central cross-dataset finding: dimension importance is domain-dependent

Team dominates when experts judge biotech/hardware proposals (highest kappa of any dimension), but Team carries no significant signal when predicting real Kickstarter funding (ρ=0.160, not significant). The reverse holds for Feasibility, which is only weakly related to expert judgment (ρ=0.156) but is the single strongest predictor of real crowdfunding success. This is a coherent, explicable pattern: VC/biotech experts weigh founder credentials heavily because execution risk is what kills those ventures; Kickstarter backers cannot verify founder credentials and instead respond to whether the product itself looks buildable and deliverable.

The central cross-dataset finding: thresholds do not transfer across domains

The GO/HOLD/NO-GO threshold (score ≥ 0.725 OR confidence ≥ 0.811) was derived entirely from the 12-proposal biotech dataset, in-sample. Applied unmodified to Kickstarter, it never fires GO once across 141 proposals — not because the underlying score carries no signal (ROC-AUC 0.764, a real and independently confirmed effect), but because the rubric's score ceiling for this domain (max observed: 0.640) sits structurally below the transferred cutoff. Recalibrating the same OR-logic rule specifically for Kickstarter, validated honestly via cross-validation, restores substantial recall (58.3%) — demonstrating this is a threshold-transfer problem, correctable, not evidence the pipeline is fundamentally broken outside its original domain.

32. Key Findings for the Paper

  • The rubric enforces a deliberate low score ceiling. The investment-scoring prompt explicitly instructs "most proposals should land in 0.40-0.70; scores above 0.80 require strong, specific evidence" and caps AI-as-product innovation at 0.42-0.56 "NO EXCEPTIONS." Any discussion of why absolute scores run low (biotech mean ≈0.68, Kickstarter max 0.640) should cite this design choice directly rather than treat it as an unexplained artifact.
  • Cross-domain generalization without retuning: a pipeline built and calibrated entirely on biotech/hardware VC proposals produces a statistically significant, positive correlation (Spearman 0.366, Holm p<0.001, n=141) with real consumer-crowdfunding outcomes it was never tuned on, and threshold-free ROC-AUC of 0.764 — independent evidence the score itself carries real information in an out-of-domain setting.
  • Dimension importance flips across domains: Team dominates the expert-judged biotech dataset but is one of the weakest, non-significant predictors of real Kickstarter outcomes; Feasibility shows the reverse pattern. A clean, quotable contrast between "what experts value" and "what crowds actually fund."
  • A threshold-transfer failure, precisely diagnosed and fixed: the in-sample-calibrated biotech threshold produces 0% recall on Kickstarter; recalibrating the identical decision-rule shape via proper cross-validation restores 58.3% recall — a controlled before/after demonstration of covariate shift in an LLM-based scoring rubric, and a methodological improvement over the biotech threshold's own in-sample-only calibration.
  • An honest overfitting demonstration, produced in this project: in-sample threshold calibration (F1=0.478) vs. properly held-out cross-validation (F1=0.364) on the same data is a small, self-contained, reproducible illustration of exactly the failure mode outcome-free validation research should guard against — arguably including the existing biotech threshold's own un-held-out calibration.
  • A quiet leak, caught by nesting the whole pipeline: a "zero-fitting" composite score that simply dropped two known-weak dimensions still leaked information through its dimension-selection step (which used the full dataset); fully nesting that selection inside cross-validation dropped ROC-AUC from an overstated 0.805 to an honest 0.773 — illustrating that leakage doesn't require model fitting to sneak in.
  • A modest, statistically-honest improvement, reported at its true confidence level: the fully-nested composite score beats the production score on point estimate (0.773 vs 0.764) with ~95% bootstrap probability of being a real effect, but does not clear a 95% significance threshold at this sample size — deliberately reported as "promising, not proven" rather than rounded up.
  • Small positive-class sizes make single train/test splits statistically unreliable: with only 24 Kickstarter successes among 141 proposals, stratified 5-fold cross-validation was necessary to obtain a stable estimate at all — directly relevant methodological guidance for any future outcome-based validation of this system on similarly rare-success datasets.
  • A real-world validation channel that scales for free: unlike the 12-proposal expert study (bounded by scarce human expert time, and explicitly not statistically well-powered at n=12), the Kickstarter real-outcome channel is free, objective, and scales to any sample size — a methodological point worth making about how LLM-based screening instruments can be validated more cheaply going forward.

33. Limitations

Limitations carried over from the existing research paper (12-proposal study)

  • n=12 is statistically underpowered (needs |ρ|≈0.73 for 80% power); the overall Spearman result does not survive Holm correction across the six-test family.
  • No second human rater exists — the expert file is "an operational reference, not universal ground truth," and no human-vs-human agreement ceiling has been established.
  • AI scores are biased low vs. human scores by 0.136 on average, a statistically robust finding (Holm p=0.009).
  • Objective and Advantages dimensions show negative or near-zero kappa/correlation with expert judgment — unresolved reliability gaps.
  • QA-only scoring (λ=0) actually reverses expert ranking (Spearman −0.325) — a component of the pipeline that would fail badly used in isolation.
  • The content-sensitivity check is explicitly prompt-coupled, not an independent test of real-world evidentiary responsiveness.
  • The groundedness audit (33 eligible claims) is a pilot, not a validated hallucination benchmark; labels are model-assisted, not independently double-annotated by humans.
  • Stage 6's dimension-commentary call runs at temperature 0.25 (non-zero) — documented but unquantified run-to-run non-determinism; repeatability is listed as future work, not yet tested.
  • Fairness risk (undemonstrated but flagged): team scoring could leak demographic/gender-coded signals from names/affiliations into execution-capacity judgments; no masking or audit currently implemented.

Limitations specific to the Kickstarter study (this session's work)

  • Precision after calibration remains modest (26-33% depending on method) — roughly 2-3 in 4 flagged campaigns still fail; not strong enough to automate a decision, only to triage.
  • Composite-score improvement (Sections 28-29) does not reach conventional statistical significance; should be reported as directionally suggestive, not confirmed, until validated on a larger sample.
  • Fold-level metrics are noisy (F1 ranges 0.0-0.47 across folds) because each held-out fold contains only ~5 real successes — wide implicit confidence intervals on any single-fold number.
  • The recalibrated Kickstarter threshold and composite score are specific to Kickstarter's score distribution; neither should be assumed to transfer to a third domain without its own recalibration and validation, by the same logic that motivated this entire study.
  • Kickstarter outcomes are driven substantially by factors outside the proposal document itself (video production, existing social following, campaign-period marketing, reward-tier pricing psychology, timing) — a text-only scoring system has a structural ceiling on achievable precision/recall regardless of calibration quality.
Deployment/governance recommendations (from the research paper's Discussion section): minimize retained proposal text beyond what's needed for audit; restrict access to intermediate pipeline artifacts (raw facts, dimension evidence, candidate answers); log the exact prompt and model version behind every recommendation; support expert override at every stage; treat dimension-specific reliability as a routing signal (route Objective/Advantages-heavy proposals to closer human review, given their weaker measured agreement); and mask or perturb demographic-adjacent cues (founder names, affiliations, nationalities) in Team-dimension scoring, logging separately when a judgment depends on affiliation rather than documented execution evidence. None of these are currently implemented; they are stated design targets for any operational deployment of this system.

A. Glossary

Spearman correlation (ρ)
Rank-based correlation: do higher-ranked items by one measure tend to be higher-ranked by another? +1 = perfect agreement, 0 = none, −1 = perfectly reversed.
Cohen's weighted κ
Agreement between two raters beyond what chance alone would produce, on binned/categorical scores; 'weighted' penalizes larger disagreements more than adjacent-bin disagreements.
ICC (Intraclass Correlation)
Measures absolute-value agreement between raters on a continuous scale (not just rank agreement) — sensitive to systematic scale offsets that Spearman would miss.
Holm correction
A family-wise multiple-testing correction, applied when running several hypothesis tests at once, more powerful than Bonferroni but still conservative; a result 'surviving Holm correction' is safer to trust than an uncorrected p-value.
Pairwise rank concordance
Of all pairs of items with a definite reference ordering, what fraction does the system order the same way? Directly reflects whether relative priority/ranking is preserved.
ROC-AUC
The probability a randomly chosen positive example scores higher than a randomly chosen negative example; 0.5 = random, 1.0 = perfect; independent of any specific decision threshold.
Average Precision
Area under the precision-recall curve; like ROC-AUC but more sensitive to performance on the rare (positive) class, useful under class imbalance.
Precision / Recall / F1
Precision: of items flagged positive, what fraction truly are? Recall: of items that are truly positive, what fraction got flagged? F1: harmonic mean of the two, useful when class imbalance makes plain accuracy misleading.
Base rate
How often the positive outcome occurs with no model involved at all — the only fair comparison point for judging whether precision/recall represents real signal or not.
K-fold cross-validation
Splits data into k folds; repeats train-on-(k-1)/test-on-1 k times, rotating which fold is held out, so every data point is evaluated exactly once by a model/threshold that never saw it during fitting.
Stratified
When splitting into folds, ensuring each fold has a proportional share of the rare (positive) class, so no fold ends up with too few positive examples to evaluate reliably.
In-sample vs. out-of-sample / held-out
In-sample: fit and evaluated on the same data (optimistic, not generalizable). Out-of-sample / held-out: evaluated on data never used during fitting (the honest estimate).
Overfitting
When a model or threshold is tuned so precisely to one dataset that it fails to generalize to new, unseen data of the same type.
Bootstrap confidence interval
Resampling the dataset with replacement many times and recomputing a statistic each time, to estimate how much that statistic would vary by chance — used here to test whether an observed improvement could just be sampling noise.
L2 regularization
A penalty added when fitting a model that discourages large coefficient values, reducing overfitting risk, especially valuable with few training examples relative to the number of features.
OR-logic threshold rule
A decision rule of the form 'predict positive if metric A clears its threshold OR metric B clears its threshold' — either condition alone is sufficient to trigger the positive prediction.
Groundedness
The fraction of a report's checkable factual claims that are actually supported by the source proposal document, as opposed to invented or unsupported.
All-or-nothing funding
Kickstarter's rule that campaigns reaching less than 100% of their goal collect $0 — makes 'funded % ≥ 100' an unambiguous binary success label.
