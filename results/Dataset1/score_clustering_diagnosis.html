Why This Is Happening

Three stacked bugs in the pipeline each independently push scores toward 0.43. Together they make every score identical.

Root Cause 1 · PRIMARY
search_hints never generated — alignment locked at 0.35
Stage 3 did not save search_hints for any dimension. Post-processing reads an empty list, making every alignment score fall to the hardcoded fallback (0.35).
Root Cause 2 · COMPOUNDING
Evidence weights zeroed out in scoring config
evidence_count, evidence_authority, and evidence_coverage are all set to 0.0. Even if evidence hints were correct, they would contribute nothing.
Root Cause 3 · MINOR
Confidence stuck at the 0.50 floor
Every LLM answer has confidence = 0.50 — the hard minimum. This could indicate the LLM is not returning the field or is consistently under-confident, adding a uniform floor contribution.

Root Cause 1 — search_hints are empty → alignment locked at 0.35

This is the dominant cause responsible for the uniform 0.35 alignment across every dimension and every proposal.

Step 1 — Stage 3 does not save search_hints to the per-proposal question set

Stage 3 (generate_questions.py) is designed to generate 6–10 short search_hints per dimension — verbatim keyword phrases that post_processing uses as authority anchors. However, the generated question set for bp1 has no search_hints field at all:

// src/data/questions/bp1/generated_questions.json
{
  "dimensions": {
    "team": {
      "dimension": "team",
      "questions": [ ... ]
      // ← no "search_hints" field
    }
  }
}

Step 2 — post_processing reads from the shared config, not the per-proposal file

The post_processing script loads authority hints from the shared config at src/data/config/question_sets/generated_questions.json, not the per-proposal file. That config has search_hints: [] for all dimensions:

// src/data/config/question_sets/generated_questions.json
{
  "team":       { "search_hints": [] },
  "objectives": { "search_hints": [] },
  "strategy":   { "search_hints": [] },
  "innovation": { "search_hints": [] },
  "feasibility":{ "search_hints": [] }
}

Step 3 — empty search_hints triggers the 0.35 hardcoded fallback

In post_processing.py, function _alignment_ratio() at line 563:

def _alignment_ratio(dim, auth_hints, answer, topic_tags, evidence_hints, ...):
    ...
    # No hints: return a neutral fallback if candidate tokens exist.
    if not auth_hints:
        return 0.35 if c_uni else 0.0  # ← ALWAYS HIT

Since auth_hints is always [], this line fires for every question, every dimension, every proposal. Alignment is unconditionally pinned at 0.35.

Step 4 — alignment is the highest-weighted scoring component

The scoring formula has alignment at the highest weight (0.30):

fields_weight config (post_processing.py line ~184)
length × 0.18
claims × 0.27
alignment × 0.30 ← LARGEST WEIGHT, always = 0.35
structure × 0.20
calibrated_confidence× 0.05
────────────────────────────────
sum = 1.00

With alignment locked at 0.35 and weight 0.30, it contributes 0.35 × 0.30 = 0.105 — identical for every question. The remaining components (claims, structure, length) contribute modest scores based on bullet count and formatting, producing the tight 0.43 cluster.

Root Cause 2 — Evidence quality weights are disabled

The scoring config at post_processing.py ~line 184 explicitly disables all evidence quality signals:

Evidence weights in fields_weight config
"evidence_count": 0.0, ← disabled
"evidence_authority": 0.0, ← disabled
"evidence_coverage": 0.0, ← disabled

A comment in the code says "In no-web mode, evidence authority/coverage are diagnostic only." This means even if the LLM's evidence_hints were high-quality, they would score 0 contribution. The scoring system has no mechanism to reward well-evidenced answers.

⚠
Root Cause 2 compounds Root Cause 1. Even after fixing search_hints, evidence quality contributes nothing to the score. Both must be fixed together to achieve meaningful differentiation.

Root Cause 3 — All confidence values at the 0.50 floor

Every single LLM answer in all_refined_items.json has confidence = 0.50, which is the hard minimum in llm_answering.py's _calibrate_confidence(). Spot check from the data:

// src/data/refined_answers/bp1/all_refined_items.json — sampled
[openai]   Q1 team  → confidence: 0.5,  quick_score: 0.7
[openai]   Q2 team  → confidence: 0.5,  quick_score: 0.7
[openai]   Q3 team  → confidence: 0.5,  quick_score: 0.7
[openai]   Q1 obj   → confidence: 0.5,  quick_score: 0.7
... (all 31 selected answers: confidence = 0.50)

The calibration range is 0.50–0.92. The LLM appears to either not be returning the confidence field (defaulting to 0.50), or is consistently outputting its minimum valid value. While confidence only has 0.05 weight, its uniform floor ensures identical contribution across all dimensions.

The aligned contribution is identical for every question. Small variations in claims count and length produce the tiny spread (0.413–0.447). The structural reason is that 30% of the score is unconditionally fixed.

Three targeted fixes, ordered by impact. Fix 1 alone resolves the clustering. Fixes 2 and 3 restore full scoring sensitivity.
